## 0. この文書の目的

紙での勤怠集計をやめ、iPad と QR カードによる打刻に置き換える。
実装に入る前に「何を作るか」を確定させるための設計書。
次回以降のセッション（Mac のデスクトップ含む）は、まずこの文書を読めば文脈が復元できる。

### 対象スタッフ

| 区分 | 人数 | 特徴 |
|---|---|---|
| 社員 | 4名 | 常時勤務。みなし残業40時間あり |
| たまに上がる社員 | 3名 | シフトに入らない日もある。温井ダムリゾート／茶ウナで随時出勤 |

常時13名 + スポット。**「シフトに入っていない人が突然出勤する」ケースが常態**であることが、この現場の最大の特徴。設計はこれを前提にする。

### 茶ウナについて

**茶ウナで働く人も、必ずまず温井ダムリゾートに来る。**したがって打刻は常に温井ダムリゾートの1台で完結し、端末を増やす必要はない。

記録には最初から「**勤務先**」列を持たせる（既定=温井ダムリゾート）。スタッフに打刻時の選択はさせない（タップが増えるため）。管理者が後から設定・変更できる形にする。


## 2. 全体構成

**Google スプレッドシート + Google Apps Script (GAS) のみで構成する。**

```
[QRカード] --かざす--> [Bluetooth 2次元スキャナ] --キーボード入力--> [iPad / Safari]
                                                                      |
                                                        google.script.run（同一オリジン）
                                                                      v
                                              [Google Apps Script Webアプリ]
                                                                      |
                                                        認証・判定・丸め・記録
                                                                      v
                                              [Google スプレッドシート（管理者のみ共有）]
                                                                      |
                                              毎月1日 3:00 時間主導トリガーで自動集計
                                                                      v
                                              [前月分 集計シート] + [管理者へメール通知]
```

### この構成を選ぶ理由

- **ランニングコスト 0 円。** サーバー契約・ドメイン・月額サービスが一切不要。Google アカウント1つで完結する。
- **転記作業が消える。** データが最初からスプレッドシート上にある。「システムから出して貼り付ける」工程が存在しない。
- **CORS の問題が起きない。** 画面も API も同じ GAS から配信されるため、`google.script.run` で直接呼べる。外部ホスティング + GAS API の構成だと POST のプリフライトで詰まりやすく、打刻の成否をブラウザ側で確認できない事故が起きうる。打刻システムで「送れたか分からない」は致命的なので、同一オリジンにする。
- **コード量が最小。** = 実装にかかる AI クレジットも最小。
- **バックアップが自動。** Google ドライブの版履歴がそのまま監査ログになる。

### 採用しなかった案

| 案 | 却下理由 |
|---|---|
| React + Supabase / Firebase | 無料枠の制限・アカウント管理・月額発生の可能性。作る量が3倍以上になりクレジットを大きく消費する |
| iPad カメラで QR を読む | カードをカメラの画角に正しくかざす動作が高齢スタッフには難しい。暗所・手ブレで読めない。Safari は BarcodeDetector API 非対応のため JS ライブラリでの処理となり、さらに読取精度が落ちる |
| 市販の勤怠SaaS | 月額が人数分かかる。細かい丸めルールが自社仕様に合わないことが多い |

### 使用する Google アカウント

**温井ダムリゾートの共有アカウントは使わない方がよい。**

理由は明快で、そのアカウントの Gmail とドライブは社員全員が見られるとのことなので、**勤怠データも全社員に見えてしまう**。勤怠データは各人の労働時間そのものであり、そこから給与が推測できる。人事情報として扱うべきもので、全社員に開示する性質のものではない。

#### 推奨する形

**勤怠専用の Google アカウントを新規作成する**（無料。例: `welmi.kintai@gmail.com`）。

| 項目 | 扱い |
|---|---|
| ログイン情報 | 管理者のみが知る |
| スプレッドシート | このアカウントのドライブに置く。共有アカウントとは完全に分離される |
| GAS の自動実行 | このアカウントの権限で動く |
| 通知メール | このアカウントから、管理者の個人アドレス宛に送る |
| 打刻画面の URL | **全員が知ってよい**。端末バインドで守られているため、URL が漏れても打刻はできない |

#### 既存のシフト表との連携

シフト表のスプレッドシートは温井ダムリゾートのアカウント上にあるが、これは問題にならない。

**シフト表を勤怠専用アカウントに「閲覧者」として共有すれば、GAS から読み取れる。**シフト表側の運用・権限は一切変えなくてよい。データの流れは片方向（シフト表 → 勤怠システム）で、勤怠データがシフト表側に漏れることはない。

これで「シフト表は全員が見られる／勤怠データは管理者だけ」という状態が両立する。


## 3. 不正打刻の防止（最重要）

「リンクを知っている人が自宅から打刻する」を防ぐ仕組み。**端末認証**で解決する。

### 3.1 端末バインド方式

1. 初回のみ、管理者が現場の iPad で打刻画面を開き、**管理者パスワード**を入力して「この端末を登録」する。
2. サーバー側でランダムな**端末トークン**（推測不可能な長い文字列）を生成し、iPad のブラウザに保存する。
3. 以降、打刻リクエストにはこの端末トークンが必ず付く。
4. **サーバーは、登録済みトークンを持たないリクエストを一切受け付けない。**

結果:
- URL が漏れても、自宅の PC・スマホから開いた人には「この端末では打刻できません」としか表示されない。打刻は成立しない。
- 登録済み端末は管理画面で一覧・失効ができる。iPad を紛失・入替した場合はその場で無効化する。
- 全打刻に「どの端末から打刻されたか」が記録される。後から監査できる。

### 3.2 QR カードの中身

- QR に埋めるのは氏名でも連番でもなく、**推測不可能なランダム文字列**（例: `wnm_a7f3c92e4b18d605`）。
- 「staff_001」のような連番にすると、他人のカードを自作できてしまう。必ずランダムにする。
- カード紛失時は管理画面でトークンを再発行 → 旧カードは即座に無効になる。
- カードには**氏名を大きく併記**する（取り違え防止・本人が自分のカードを識別するため）。

### 3.3 補助的な対策（任意）

- **IP 制限**: 施設のグローバル IP からのアクセスのみ許可。ただしプロバイダの IP が変わると全員打刻できなくなるため、端末バインドの補助としてのみ使う。既定は OFF。
- **代理打刻の抑止**: 物理カードを預ければ代理打刻は理論上可能。完全には防げないため、全打刻に時刻・端末を記録し「後から検証できる」状態を作る方針とする。運用ルール（カードは本人が保持）と併せて担保する。

## 4. 打刻の操作（高齢スタッフ対応の中核）

### 4.1 スタッフの操作は「カードをかざす」だけ

**ボタンを押す必要すらない。1アクションで完結する。**

- 出勤か退勤かは**システムが自動判定**する。
  - その日まだ出勤記録がない → **出勤**
  - すでに出勤済みで退勤記録がない → **退勤**
- スタッフは「今日は出勤ボタンだっけ、退勤ボタンだっけ」と考える必要がない。ここが理解のハードルを一番下げる。

### 4.2 打刻後の画面

かざした瞬間に全画面で表示する。

```
┌──────────────────────────────┐
│                              │
│      田中 太郎 さん          │   ← 72px 太字
│                              │
│      おはようございます       │
│                              │
│    ✅ 出勤 9:00 打刻しました  │   ← 96px。出勤=青 / 退勤=橙
│                              │
└──────────────────────────────┘
```

- 文字は特大。色で出勤/退勤を区別（文字が読みづらい方でも色で分かる）。
- **音を鳴らす**（成功音）。さらに**音声で読み上げる**：「たなかさん、しゅっきん、くじ」。Web Speech API で追加費用なし。**高齢の方は音のフィードバックが最も安心感につながる。**
- 5秒後に自動で待機画面（大きな時計＋「カードをかざしてください」）へ戻る。

### 4.3 誤操作への対応

| 状況 | 挙動 |
|---|---|
| 続けて2回かざした | 直近5分以内の同一人物の再スキャンは無視し「すでに打刻済みです（9:00 出勤）」と表示 |
| 未登録・失効したカード | 「このカードは使えません。担当者にお伝えください」と表示。打刻はしない |
| 前日の退勤打刻がない状態で出勤 | 出勤打刻は通したうえで「前回の退勤打刻がありません。担当者にお伝えください」を併記。管理者側に「要修正」として上がる |
| 通信が切れている | 打刻を端末内に一時保存し、復旧後に自動送信。画面には「打刻しました（送信待ち）」と表示して、スタッフを不安にさせない |

### 4.4 保険としての「名前ボタン方式」

カード忘れ・スキャナ故障に備え、**同じ画面に名前ボタン方式も内蔵しておく**（既定は非表示、管理者が有効化できる）。
名前の大きなボタンが並ぶだけの画面で、これも1タップで完結する。運用の停止を防ぐための保険。

---

### 4.5 QR をかざすと名前は自動で出るか

**出る。**QR カードには推測不可能なランダム文字列だけが入っており、システムがスタッフ名簿と照合して氏名を表示する。スタッフ側の操作も入力も一切ない。

```
[カードをかざす] → スキャナが "wnm_a7f3c92e4b18d605" を送信
                 → システムが名簿と照合 → 「田中 太郎さん」と判明
                 → その日の記録を見て 出勤/退勤 を自動判定
                 → 全画面表示 +音声「たなかさん、しゅっきん、くじ」
```

氏名を変更してもカードの作り直しは不要（カードの文字列と名簿を紐づけているだけなので、名簿側を直せば表示も変わる）。

### 4.6 スポット・臨時スタッフの打刻

その日限りで入る方のためにカードを印刷するのは現実的でないため、**予備カード方式**を使う。

1. あらかじめ「**臨時1**」〜「**臨時5**」と書いたカードを5枚ほど作っておく（一度作れば使い回せる）
2. スポットの方が来たら、管理者が管理画面で氏名を登録し、「臨時1 = 山田花子（本日）」と紐づける（**10秒程度**）
3. その方は「臨時1」のカードをかざすだけ。**常時スタッフと操作がまったく同じになる**
4. 紐づけは翌朝の日次バッチで自動解除され、カードは再利用できる

スポットの方も高齢である可能性を考えると、**全員の操作を「かざすだけ」に統一できる**のが大きい。名前をタップして探す方式より確実。

予備が足りない・カードを渡し損ねた場合の保険として、名前ボタン方式も併用できる（4.4）。


## 5. 打刻用の端末と機材

### 5.1 前提の変更: iPad はチェックインと共用

現場の iPad はゲストのチェックインでも使うため、**1つのアプリに固定するロック（アクセスガイド）は使えない**。
これにより新たな論点が2つ生じる。

1. **打刻画面が常に手前にあるとは限らない。** スタッフが打刻に来たとき、iPad はチェックイン画面を表示している。打刻するには「ホームに戻る → 打刻アイコンを探してタップ → カードをかざす」となり、**操作が1アクションから3アクションに増える**。高齢スタッフにとってはここが一番の障壁になる。
2. **端末を自由に触れる状態になる。** 誤って別の画面を開く、設定を変えてしまう、といった事故が起きうる。

### 5.2 打刻端末の選択肢と費用

| 案 | 内容 | 追加費用 |
|---|---|---|
| **案A** | 打刻専用端末をスタッフ通用口に固定設置 | 端末代 + スキャナ代 |
| **案B** | 既存 iPad を共用（チェックインと兼用） | スキャナ代のみ |
| **案C（推奨）** | **まず案Bで始め、現場テストで不便なら案Aへ移行** | スキャナ代のみ（当面） |

**案C を推奨する理由**: 打刻画面は同じものを使うので、後から専用端末を足しても作り直しは一切発生しない。「3アクションが実際に障害になるか」は現場で試さないと分からないため、先にお金をかけない。実際に高齢スタッフが迷うようなら、そのとき端末を買えばよい。

### 5.3 専用端末を用意する場合の費用目安

| 選択肢 | 目安 | 備考 |
|---|---|---|
| 使っていない古い iPhone / iPad | **0円** | 最有力。打刻画面はブラウザで動くだけなので、古い機種で十分。ホーム画面に置いて常時表示にする |
| 中古 iPad（第7世代 32GB Wi-Fi など） | 14,000円前後〜 | 画面が大きく見やすい。イオシス等の中古販売店 |
| Amazon Fire HD タブレット（新品） | 1万円前後（セール時さらに安い） | **Google アカウント不要**（スタッフはログインしないため問題にならない）。ブラウザが動けば要件は満たす |
| 廉価 Android タブレット（新品） | 1万円台〜 | 同上 |

打刻画面は**ただのWebページ**なので、端末の性能はほとんど関係ない。手元に眠っている端末があればそれが最も安い。


### 5.4 スキャナ: Tera HW0002（確定）

**Amazon.co.jp / ¥5,998（税込）/ ASIN: B07T9J9Q99 / メーカー: Tera**

要件を満たしていることを確認済み。

| 要件 | 判定 | 内容 |
|---|---|---|
| 2次元コード（QR）対応 | ✅ | QR Code / Data Matrix / PDF417 / Aztec / Maxicode。1次元も対応 |
| Bluetooth HID 対応 | ✅ | USB有線 / 2.4GHz / Bluetooth の3方式。iOS・Android・Windows 互換 |
| iPad 対応 | ✅ | 互換デバイスに「パソコン／タブレット／スマホ」の明記あり |
| 電源 | ✅ | バッテリー式（充電式） |
| **技適取得済み** | ✅ | **日本国内で合法に使える。無線機器ではここが重要** |
| 日本語説明書 | ✅ | 付属 |
| 保証 | ✅ | メーカー1年保証 |
| 実績 | ✅ | 評価3.9（445件）、バーコードスキャナー売れ筋2位、過去1か月で200点以上 |

#### この機種が今回の用途に特に向いている理由

**スタンドが付属し、自動検知スキャンモードがある。**スタンドに置いておけば、**カードをかざすだけで自動的に読み取る**。トリガーを引く必要がない。

これはまさに今回の設計意図（操作は1アクション）と一致する。高齢のスタッフに「引き金を引く」動作を説明する必要がなくなる。

#### 注意点

- 商品説明に「**iPad やスマホに日本語文字の入力には対応しません**」とある。→ **今回は問題にならない。**QR に入れるのは英数字のランダム文字列だけで、日本語は一切含まないため。氏名は QR ではなくシステム側の名簿から引く。
- Bluetooth HID キーボードとして接続されるため、**iPad のソフトウェアキーボードが画面に出なくなる**。打刻画面にとってはむしろ好都合。
- 評価3.9 はこの価格帯として標準的。445件のレビューがあり、売れ筋上位という実績の方を重視してよい。

#### 購入後の設定

1. **HID（キーボード）モード**に設定する
2. **Bluetooth 接続**で iPad とペアリングする
3. **自動検知スキャンモード**に設定する
4. スタンドに設置し、カードをかざす高さに調整する

設定は付属の日本語説明書にある設定用QRコードを読ませるだけで完了する。

#### QRカードについて

- 名刺サイズに印刷してラミネート。**氏名を大きく併記**する
- 首下げストラップ推奨
- 発行対象: 常時勤務の13名 + 予備カード「臨時1〜5」


### 5.5 将来の移行余地について

打刻画面は Google Apps Script から配信するため、Safari で開くとアドレスバーが表示される（GAS の画面は iframe 内で動く仕様上、ホーム画面追加でも全画面アプリのようには開けない）。
スクリーンタイム制限で実害は塞げるが、もし現場テストでアドレスバーが問題になれば、**画面だけを Cloudflare Pages（無料）に移して完全な全画面アプリにできる**。その場合も変更するのは通信部分だけで済むよう、**API 呼び出しを1ファイルに隔離して実装する**。フェーズ1の時点では GAS のみで進め、余計な構成を先に増やさない。


## 6. シフトと時刻の丸め

### 6.1 シフト: 既存のシフト表をそのまま読む

**シフト入力は一切増やさない。今使っているシフト表スプレッドシートを、勤怠システムが裏で読む。**

添付いただいたシフト表を確認したところ、そのまま機械的に読み取れる形になっていた。運用を変える必要はない。

#### 現在の運用（変更なし）

```
毎月5日  リマインくんが LINE グループに「前半のシフト提出」と投稿
毎月25日 同じく「後半のシフト提出」
         ↓
高齢スタッフを含む全員が LINE グループで休み希望を伝える
         ↓
担当スタッフが Google スプレッドシートに手入力してシフトを作成
         ↓
完成したシフト表を画像にして LINE グループへ共有
```

**この流れは1ミリも変えない。**勤怠システムがこのスプレッドシートを読むだけ。

#### シフト表の構造（確認済み）

| 位置 | 内容 |
|---|---|
| シート名 | `9月前半` `9月後半` のように半月ごと |
| 3行目 | タイトルと凡例（`×`=休み希望日、`-`=休み、`⚪︎`=出勤） |
| 6行目 | 曜日 |
| 7行目 | 日付 |
| 8〜19行目 | スタッフ名（橋本／三瀧／沖田／ひかる／三村／ゆかちゃん／冨樫／丸崎／えみこ／月待／隈元／森脇） |
| 20〜21行目 | 温井・茶ウナの人数集計 |
| 22行目 | 備考 |

**すでにシフト記号が運用されている。**`早` `通` `遅` `休` `希望休` `⚪︎` `×` `協力隊` など。私が提案しようとしていた「記号でシフトを表す」方式が、既に実践されていた。あとは記号の意味（`早`＝何時から何時か）を一度登録するだけで、このシートがそのまま機械可読になる。

#### 読み取りルール

| セルの値 | 扱い |
|---|---|
| `早` `通` `遅` などの登録済み記号 | その記号の時刻をシフトとして採用。**丸め（早出切り捨て・残業判定）が効く** |
| `9:00〜` のような直接入力 | 書かれた時刻をシフトとして採用 |
| `⚪︎` `協力隊` など時刻の分からない出勤 | 出勤予定ありとして扱うが、**実打刻をそのまま採用**（丸めなし） |
| `休` `希望休` `×` `-` 空欄 | 休み。打刻があれば「シフト外」として実打刻を採用 |

**判断がつかない値は、勝手に切り捨てず実打刻を採用する。**これが安全側の設計。

#### 実装上の配慮

- **氏名の表記ゆれを吸収する。**シフト表は「ひかる」「ゆかちゃん」など愛称混在なので、スタッフ名簿に「シフト表での表記」列を持たせて対応付ける。
- **行番号は固定しない。**A列の氏名を探して行を特定する。人が増減しても壊れない。
- **シート名で月を判定する。**`10月後半` のシートのタイトルセルが `10月前半シフト` のままになっている箇所があった（コピー時の直し忘れ）。タイトルセルではなくシート名を見るようにすれば影響を受けない。
- シート名の付け方が `1月` `2月シフト` のように揺れている月もあるため、`N月前半` `N月後半` を基本としつつ、読めないシートは警告を出して無視する。

#### 唯一の穴: パートの勤務時間

パートの方の行は `⚪︎`（出勤）だけで、**何時から何時かがシフト表に入っていない**。一方で**パートは時給制なので、早出の切り捨ては直接お金に関わる**。ここだけが噛み合っていない。

対処の選択肢（後から決めればよい。フェーズ1は実打刻採用で動く）:

| 案 | 内容 | 手間 |
|---|---|---|
| **① `⚪︎` を `早` `遅` などの記号に変える** | 入力する文字数は同じ。丸めが効くようになる | ほぼゼロ |
| ② `9:00〜17:00` と直接書く | 既に隈元さんの行で使われている書き方 | 少し増える |
| ③ そのまま `⚪︎` で運用 | 実打刻をそのまま採用。早出は切り捨てられない | ゼロ |

**①を推奨する。**打つ文字数は変わらないのに、当初の要件だった「早く来ても切り捨てる」が効くようになる。ただしフェーズ1では③のまま動かし、実際の打刻データを見てから決めても遅くない。


### 6.2 丸めルール

| 状況（例: 9:00〜17:00 のシフト） | 記録される実打刻 | 集計に使う時刻 |
|---|---|---|
| 8:40 に出勤打刻（早出） | 8:40 | **9:00**（早出分は切り捨て） |
| 9:12 に出勤打刻（遅刻） | 9:12 | 9:12 ＋ 遅刻12分として記録 |
| 16:30 に退勤打刻（早退） | 16:30 | 16:30 ＋ 早退30分として記録 |
| 17:10 に退勤打刻（猶予内） | 17:10 | **17:00**（猶予15分以内は定時扱い） |
| 17:45 に退勤打刻（残業） | 17:45 | 17:00 ＋ **残業45分（承認待ち）** |

**実打刻は必ず生データとして残す。**丸めた結果だけを保存すると、後から検証できず労務上のリスクになる。

**猶予15分**（設定変更可）は、片付けや着替えで数分過ぎるだけのケースを毎回残業扱いにしないための緩衝。

### 6.3 残業の扱い（方式② 自動承認＋却下で確定）

スタッフに追加操作はさせない。**打刻は1アクションのまま**で、定時+15分を超えた退勤打刻は自動的に残業として記録される。

- 定時+15分までは定時扱い（切り捨て）。片付けや着替えでの数分の超過を毎回残業にしないための緩衝
- それを超えた分は**自動的に承認済みとして加算**される
- 管理者は一覧を見て、**おかしいものだけ却下**する
- 月末の締め処理の前に「今月の残業一覧」をメールで送り、確認を促す。**確認する機会は作るが、確認しなくても止まらない**

承認漏れが賃金未払いにならない、払う方向に倒れる設計。

### 6.3.1 みなし残業40時間の扱い

**社員の月給には既に40時間分のみなし残業が含まれている。**これは集計に反映する必要がある。

#### 仕組み

スタッフ名簿に「**みなし残業時間数**」の列を持たせる。

| 区分 | みなし残業 | 意味 |
|---|---|---|
| 社員 | 40時間 | 40時間までは月給に含まれるため追加支給なし |
| パート・アルバイト | 0時間 | 時給制。残業は全額が追加支給の対象 |

#### 月次集計に出す列

| 列 | 内容 |
|---|---|
| 残業時間 | その月に実際に発生した残業の合計 |
| みなし残業枠 | 40時間（パートは0） |
| 枠の消化率 | 例: 28.5h / 40h = 71% |
| **みなし超過分** | **40時間を超えた分。追加支給の対象** |

#### これがシステム化で一番効くところ

**みなし残業を超えた分の割増賃金は、法律上どのみち別途支払う義務がある。**紙の集計では40時間を超えたかどうかを正確に把握するのが難しく、超過に気づかないまま月が終わりやすい。

このシステムなら:
- 月次集計で**超過分が自動的に金額計算まで含めて出る**
- さらに**月の途中で枠に近づいた時点でアラートを出せる**（例: 32時間＝80%到達で管理者にメール）。超えてから気づくのではなく、シフトを調整する余地が生まれる

> 参考: 36協定の原則上限は月45時間。みなし40時間はその大半を占める枠なので、超過の把握は労務管理上そもそも重要度が高い。


### 6.4 休憩

**休憩の打刻はさせない**（操作を増やすと必ず押し忘れが出る）。実労働時間から自動控除する。

- 既定: 実働6時間超 → 45分控除 / 8時間超 → 60分控除
- 設定シートで変更可能

※ このルールは労働基準法第34条の下限に沿った既定値。実際の就業規則に合わせて要確認。

## 7. 月次締めと出力

- **毎月1日 午前3時**、GAS の時間主導トリガーが自動実行される。
- 前月分を集計し、指定スプレッドシートに **「2026年08月」** という名前のシートを新規作成する。
- 完了後、管理者にメールで通知（GAS の MailApp、無料）。

### 7.1 サマリー表（スタッフ1人1行）

| 氏名 | 区分 | 出勤日数 | 所定内労働時間 | 残業時間 | みなし枠 | 消化率 | **みなし超過** | 遅刻(回/分) | 早退(回/分) | 欠勤 | 打刻漏れ | シフト外打刻 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|

- **みなし超過** = 追加支給の対象になる時間。ここが 0 でない人はすぐ分かるよう強調表示する
- **欠勤** = シフトがあるのに打刻がない日
- **打刻漏れ** = 出勤のみ／退勤のみの日
- **シフト外打刻** = シフトのない日の打刻（たまに上がる社員・スポットの方は通常ここに入る）


### 7.2 日別明細（1人1日1行）

| 日付 | 曜 | シフト | 出勤打刻 | 退勤打刻 | 採用出勤 | 採用退勤 | 休憩 | 実働 | 残業 | 状態 | 備考 |
|---|---|---|---|---|---|---|---|---|---|---|---|

「打刻」列が生データ、「採用」列が丸め後。両方載せることで、なぜその時間になったかが一目で分かる。

### 7.3 管理者のみ閲覧できる仕組み

- スプレッドシートを**管理者の Google アカウントのみに共有**する。
- スタッフは Google アカウントを使わない（カードをかざすだけ）ので、**そもそもデータへのアクセス経路が存在しない**。
- ダウンロードはスプレッドシートの標準機能（ファイル → ダウンロード → Excel / CSV / PDF）でそのまま行える。専用機能を作る必要はない。

### 7.4 記録の保存

労働時間の記録は保存義務がある（賃金台帳等は5年、当分の間3年）。スプレッドシート上に year ごとに残り続けるため、運用上は自動的に満たされる。年度ごとにファイルを分けるかは運用で決める。

## 8. 打刻忘れ・カード忘れへの対応

紙の運用と最も差が出るところ。**管理者がスプレッドシートを直接手入力することはしない。**専用の修正画面から直す。

### 8.1 まず「気づけるようにする」

打刻忘れは必ず起きる前提で、**その日のうちに分かる**ようにする。今の紙運用では月末の集計時にまとめて発覚するが、そのときには本人も何時に帰ったか覚えていない。ここが一番の改善点。

- **毎日の営業終了後（既定 翌朝4:00）にバッチが走り**、退勤打刻のない記録を「未完了」として確定させる。
  ※ このバッチがないと、翌日の出勤打刻が前日の「退勤」と誤判定されてしまう。判定は必ず当日の記録だけを見る。
- 未完了があれば**管理者にメールで通知**する（「9/7 田中太郎さん 退勤打刻なし」）。翌朝には把握できる。
- 翌朝そのスタッフがカードをかざしたとき、打刻画面にも表示する。
  →「昨日の退勤打刻がありません。担当者にお伝えください」（出勤打刻自体は通常どおり通す）

### 8.2 誰がどう直すか

**管理者が修正画面から直す。**スプレッドシートには直接触らない。

修正画面の操作:

1. 管理画面の「要修正」一覧に、未完了の日が並ぶ（何件あるかバッジ表示）
2. 該当行をタップすると修正フォームが開く
3. **退勤時刻の欄には、その日のシフトの終業時刻が初期値として入っている**
4. 本人に確認して、その時刻でよければ**そのまま保存（ワンタップ）**。違えば時刻を直す
5. 理由を選ぶ（打刻忘れ／カード忘れ／機器の不調／その他）
6. 保存

**管理者の手間はワンタップ〜数秒**で済む。スプレッドシートを開いてセルを探して打ち込む、という作業は発生しない。

### 8.3 修正の記録が必ず残る

修正すると以下が自動で記録される。

| 記録される内容 |
|---|
| 元の値（打刻がなかったこと） |
| 修正後の値 |
| 修正した人 |
| 修正した日時 |
| 修正理由 |

- **元の打刻データは消えない。**修正は上書きではなく追記として扱う。
- 月次の日別明細には「状態」列に **修正済（打刻忘れ）** と表示され、備考に理由が入る。
- なぜ手入力されたのかが後から誰でも追える状態にする。労基署対応や賃金トラブル時の説明責任の観点で、これは省略できない。

**スプレッドシートを直接手入力させない理由**もここにある。直接編集では「誰がいつ何を変えたか」が残らず、丸めや休憩控除の計算も通らず、行や数式を壊す事故も起きる。修正画面を経由すれば、手入力であっても正規の記録として扱える。

### 8.4 その他の例外ケース

| ケース | 対応 |
|---|---|
| カードを忘れた | 管理者が管理画面から代理打刻する。履歴に「管理者代理」と残る。名前ボタン方式を有効化して本人に押してもらってもよい |
| カードを紛失した | 管理画面で再発行。旧カードは即座に無効になる |
| 出勤打刻を忘れた | 退勤打刻だけが残る。8.2 と同じ流れで、出勤時刻の欄にシフトの始業時刻が初期値で入る |
| 出勤も退勤も忘れた | シフトはあるが打刻が一切ない日として「欠勤？」で一覧に上がる。管理者が実際に出勤していたなら修正画面から両方入力する |
| スキャナが壊れた | 管理者が名前ボタン方式を有効化する。復旧までタップ操作で運用を継続できる |
| 打刻を忘れたまま月末を迎えた | 月次集計に「要修正 ◯件」として明示される。締め処理は未修正でも走るが、警告は消えない |

### 8.5 「自動でシフト通りに埋める」を既定にしない理由

打刻がない日をシフトの定時で自動的に埋めてしまえば管理者の手間はゼロになるが、これは採用しない。実際には残業していた・早退していた場合に**実態と違う労働時間が記録として確定してしまう**ためで、賃金の未払いにも過払いにもつながる。

代わりに **8.2 のとおり「シフトの時刻を初期値として提示し、人が確認して確定する」**形にする。手間はほぼ変わらないまま、記録としては「人が確認したもの」になる。

### 移行の進め方（紙との並行運用はしない）

紙との1か月並行は負担が大きいため行わない。代わりに**テストを重ねてから全面切替**する。

| 段階 | 内容 | 期間 |
|---|---|---|
| 1 | 管理者が自分で毎日打刻し、集計結果を確認する | 1週間 |
| 2 | 協力してもらえるスタッフ2〜3名を加えて試す。**高齢のスタッフを1名は必ず入れる**（ここで分かることが最も多い） | 1週間 |
| 3 | 全員に展開。その月から本番運用 | — |

**紙の代わりの保険**:
- 打刻データは毎日スプレッドシートに溜まるので、**週に1回眺めるだけ**で異常に気づける。紙で二重に記録する必要はない。
- 未完了の打刻はその日のうちにメールで通知される（8.1）。月末にまとめて発覚することがない。
- 初月の月次集計が出た直後に、管理者が1回だけ目視で確認する。

段階2で高齢スタッフに実際に触ってもらうことが、この移行で最も重要な工程。ここで「かざすだけ」が本当に伝わるかが分かる。


## 11. 運用上の設定（実装とは別に必ずやること）

### 打刻専用端末を用意する場合（案A）

- **アクセスガイドを有効にする**（設定 → アクセシビリティ → アクセスガイド）。打刻画面から出られないよう固定する。専用機なのでこれが使える。
- 電源に挿しっぱなし、自動ロック OFF、画面の明るさ固定。
- スタッフ通用口の、出入りの動線上に固定設置する。

### iPad を共用する場合（案B）

- **アクセスガイドは使わない**（チェックイン業務が止まるため）。
- 代わりに**スクリーンタイムの「許可されたWebサイトのみ」**を設定する。打刻システムとチェックインシステムだけを許可し、スクリーンタイム用パスコードはスタッフに教えない。
- 打刻画面を**ホーム画面に追加**し、アイコンを1ページ目の左上に置く。
- 自動ロック OFF、電源に挿しっぱなし。

### 共通

- Wi-Fi の安定を確認する。切れても打刻は端末内に貯まり復旧後に自動送信されるが、常時つながっている方がよい。
- 管理者のメール通知先を設定する（毎日の未完了通知・月次完了通知が届く）。

## 13. 使用する Claude モデルの指針（クレジット節約）

### 前提: このシステムは**動作に AI を一切使わない**

打刻・判定・集計はすべて通常のプログラム処理。AI を使うのは**作るときだけ**。
したがって**稼働後の AI 費用は 0 円**。ここが SaaS との大きな違い。

### 作業別の使い分け

| 作業 | 推奨モデル | 理由 |
|---|---|---|
| 設計・仕様確定・丸め計算・締め処理などのロジック | **Opus 5** | ここをケチると設計ミスで作り直しになり、結果的に高くつく |
| 画面の HTML/CSS、単純な CRUD、文言修正 | **Sonnet 5**（`/model sonnet`） | Opus の半分以下の単価。この用途では品質差がほぼ出ない |
| 整形・リネームなどの単純作業 | **Haiku 4.5** | 最安 |

参考単価（1Mトークンあたり／入力・出力）: Opus 5 = $5 / $25、Sonnet 5 = $2 / $10、Haiku 4.5 = $1 / $5

### 消費を減らす実践的なコツ

1. **まとめて依頼する。** 「フェーズ1を全部作って」の方が、細かく何往復もするより圧倒的に安い。往復のたびにリポジトリを読み直すのが最大の無駄。
2. **セッションを分けすぎない。** 1つの作業は1セッションで終わらせる。
3. **この設計書をリポジトリに置いておく。** 次のセッションで一から説明し直す必要がなくなる（今回これを実施済み）。
4. **実装は Sonnet で始め、詰まったら Opus に上げる。** `/model` でいつでも切り替えられる。
5. 動作確認・微修正だけの日は Sonnet か Haiku で十分。
