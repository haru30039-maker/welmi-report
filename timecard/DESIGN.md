## 0. この文書の目的

紙での勤怠集計をやめ、iPad と QR カードによる打刻に置き換える。
実装に入る前に「何を作るか」を確定させるための設計書。
次回以降のセッション（Mac のデスクトップ含む）は、まずこの文書を読めば文脈が復元できる。

| 項目 | 決定 |

| 打刻方法 | QR カードをスキャナに読ませる |
| シフト | 固定シフトの人と、月ごとのシフト表の人が混在 |

## 2. 全体構成

**Google スプレッドシート + Google Apps Script (GAS) のみで構成する。**

```
[QRカード] --かざす--> [Bluetooth 2次元スキャナ] --キーボード入力--> [iPad / Safari]
                                                                      |
                                                        google.script.run（同一オリジン）
                                                                      v
                                              [Google Apps Script Webアプリ]
                                                                      |
                                                        認証・判定・丸め・記録
                                                                      v
                                              [Google スプレッドシート（管理者のみ共有）]
                                                                      |
                                              毎月1日 3:00 時間主導トリガーで自動集計
                                                                      v
                                              [前月分 集計シート] + [管理者へメール通知]
```

### この構成を選ぶ理由

- **ランニングコスト 0 円。** サーバー契約・ドメイン・月額サービスが一切不要。Google アカウント1つで完結する。
- **転記作業が消える。** データが最初からスプレッドシート上にある。「システムから出して貼り付ける」工程が存在しない。
- **CORS の問題が起きない。** 画面も API も同じ GAS から配信されるため、`google.script.run` で直接呼べる。外部ホスティング + GAS API の構成だと POST のプリフライトで詰まりやすく、打刻の成否をブラウザ側で確認できない事故が起きうる。打刻システムで「送れたか分からない」は致命的なので、同一オリジンにする。
- **コード量が最小。** = 実装にかかる AI クレジットも最小。
- **バックアップが自動。** Google ドライブの版履歴がそのまま監査ログになる。

### 採用しなかった案

| 案 | 却下理由 |
|---|---|
| React + Supabase / Firebase | 無料枠の制限・アカウント管理・月額発生の可能性。作る量が3倍以上になりクレジットを大きく消費する |
| iPad カメラで QR を読む | カードをカメラの画角に正しくかざす動作が高齢スタッフには難しい。暗所・手ブレで読めない。Safari は BarcodeDetector API 非対応のため JS ライブラリでの処理となり、さらに読取精度が落ちる |
| 市販の勤怠SaaS | 月額が人数分かかる。細かい丸めルールが自社仕様に合わないことが多い |

## 3. 不正打刻の防止（最重要）

「リンクを知っている人が自宅から打刻する」を防ぐ仕組み。**端末認証**で解決する。

### 3.1 端末バインド方式

1. 初回のみ、管理者が現場の iPad で打刻画面を開き、**管理者パスワード**を入力して「この端末を登録」する。
2. サーバー側でランダムな**端末トークン**（推測不可能な長い文字列）を生成し、iPad のブラウザに保存する。
3. 以降、打刻リクエストにはこの端末トークンが必ず付く。
4. **サーバーは、登録済みトークンを持たないリクエストを一切受け付けない。**

結果:
- URL が漏れても、自宅の PC・スマホから開いた人には「この端末では打刻できません」としか表示されない。打刻は成立しない。
- 登録済み端末は管理画面で一覧・失効ができる。iPad を紛失・入替した場合はその場で無効化する。
- 全打刻に「どの端末から打刻されたか」が記録される。後から監査できる。

### 3.2 QR カードの中身

- QR に埋めるのは氏名でも連番でもなく、**推測不可能なランダム文字列**（例: `wnm_a7f3c92e4b18d605`）。
- 「staff_001」のような連番にすると、他人のカードを自作できてしまう。必ずランダムにする。
- カード紛失時は管理画面でトークンを再発行 → 旧カードは即座に無効になる。
- カードには**氏名を大きく併記**する（取り違え防止・本人が自分のカードを識別するため）。

### 3.3 補助的な対策（任意）

- **IP 制限**: 施設のグローバル IP からのアクセスのみ許可。ただしプロバイダの IP が変わると全員打刻できなくなるため、端末バインドの補助としてのみ使う。既定は OFF。
- **代理打刻の抑止**: 物理カードを預ければ代理打刻は理論上可能。完全には防げないため、全打刻に時刻・端末を記録し「後から検証できる」状態を作る方針とする。運用ルール（カードは本人が保持）と併せて担保する。

## 4. 打刻の操作（高齢スタッフ対応の中核）

### 4.1 スタッフの操作は「カードをかざす」だけ

**ボタンを押す必要すらない。1アクションで完結する。**

- 出勤か退勤かは**システムが自動判定**する。
  - その日まだ出勤記録がない → **出勤**
  - すでに出勤済みで退勤記録がない → **退勤**
- スタッフは「今日は出勤ボタンだっけ、退勤ボタンだっけ」と考える必要がない。ここが理解のハードルを一番下げる。

### 4.2 打刻後の画面

かざした瞬間に全画面で表示する。

```
┌──────────────────────────────┐
│                              │
│      田中 太郎 さん          │   ← 72px 太字
│                              │
│      おはようございます       │
│                              │
│    ✅ 出勤 9:00 打刻しました  │   ← 96px。出勤=青 / 退勤=橙
│                              │
└──────────────────────────────┘
```

- 文字は特大。色で出勤/退勤を区別（文字が読みづらい方でも色で分かる）。
- **音を鳴らす**（成功音）。さらに**音声で読み上げる**：「たなかさん、しゅっきん、くじ」。Web Speech API で追加費用なし。**高齢の方は音のフィードバックが最も安心感につながる。**
- 5秒後に自動で待機画面（大きな時計＋「カードをかざしてください」）へ戻る。

### 4.3 誤操作への対応

| 状況 | 挙動 |
|---|---|
| 続けて2回かざした | 直近5分以内の同一人物の再スキャンは無視し「すでに打刻済みです（9:00 出勤）」と表示 |
| 未登録・失効したカード | 「このカードは使えません。担当者にお伝えください」と表示。打刻はしない |
| 前日の退勤打刻がない状態で出勤 | 出勤打刻は通したうえで「前回の退勤打刻がありません。担当者にお伝えください」を併記。管理者側に「要修正」として上がる |
| 通信が切れている | 打刻を端末内に一時保存し、復旧後に自動送信。画面には「打刻しました（送信待ち）」と表示して、スタッフを不安にさせない |

### 4.4 保険としての「名前ボタン方式」

カード忘れ・スキャナ故障に備え、**同じ画面に名前ボタン方式も内蔵しておく**（既定は非表示、管理者が有効化できる）。
名前の大きなボタンが並ぶだけの画面で、これも1タップで完結する。運用の停止を防ぐための保険。

## 6. シフトと時刻の丸め

### 6.1 シフトの持ち方（固定・不定期の混在に対応）

2階建てにする。

1. **基本シフト**（スタッフ名簿に登録）: 曜日ごとの始業・終業時刻。固定勤務の社員はこれだけで完結し、毎月の入力が不要。
2. **月間シフト表**（別シート）: 日付・氏名・始業・終業を入力。パートの方はこちらを使う。
3. 判定順序: **月間シフト表に該当日の指定があればそれを優先**、なければ基本シフトを使う。

どちらにも指定がない日に打刻された場合は「**シフト外**」として記録し、勝手に切り捨てず、月次集計で管理者に警告として表示する。

### 6.2 丸めルール

| 状況（例: 9:00〜17:00 のシフト） | 記録される実打刻 | 集計に使う時刻 |
|---|---|---|
| 8:40 に出勤打刻（早出） | 8:40 | **9:00**（早出分は切り捨て） |
| 9:12 に出勤打刻（遅刻） | 9:12 | 9:12 ＋ 遅刻12分として記録 |
| 16:30 に退勤打刻（早退） | 16:30 | 16:30 ＋ 早退30分として記録 |
| 17:10 に退勤打刻（猶予内） | 17:10 | **17:00**（猶予15分以内は定時扱い） |
| 17:45 に退勤打刻（残業） | 17:45 | 17:00 ＋ **残業45分（承認待ち）** |

**実打刻は必ず生データとして残す。**丸めた結果だけを保存すると、後から検証できず労務上のリスクになる。

**猶予15分**（設定変更可）は、片付けや着替えで数分過ぎるだけのケースを毎回残業扱いにしないための緩衝。

### 6.3 残業の申請・承認

スタッフに追加操作はさせない。**打刻は1アクションのままにする。**

1. 終業＋猶予を超えた退勤打刻は、**自動的に「残業（承認待ち）」として積まれる**。
2. 管理者は管理画面またはスプレッドシート上で一覧を確認し、**承認 / 却下 / 時間修正**する。
3. 集計に加算されるのは**承認済みの分のみ**。
4. 未承認のまま月末を迎えた分は集計上0分（定時扱い）とし、**「未承認 ◯件」を集計シートに明示**する。黙って消さない。

### 6.4 休憩

**休憩の打刻はさせない**（操作を増やすと必ず押し忘れが出る）。実労働時間から自動控除する。

- 既定: 実働6時間超 → 45分控除 / 8時間超 → 60分控除
- 設定シートで変更可能

※ このルールは労働基準法第34条の下限に沿った既定値。実際の就業規則に合わせて要確認。

## 7. 月次締めと出力

- **毎月1日 午前3時**、GAS の時間主導トリガーが自動実行される。
- 前月分を集計し、指定スプレッドシートに **「2026年08月」** という名前のシートを新規作成する。
- 完了後、管理者にメールで通知（GAS の MailApp、無料）。

### 7.1 サマリー表（スタッフ1人1行）

| 氏名 | 出勤日数 | 所定内労働時間 | 残業時間(承認済) | 遅刻(回/分) | 早退(回/分) | 欠勤 | 打刻漏れ | 未承認残業 |
|---|---|---|---|---|---|---|---|---|

- **欠勤** = シフトがあるのに打刻がない日
- **打刻漏れ** = 出勤のみ／退勤のみの日

### 7.2 日別明細（1人1日1行）

| 日付 | 曜 | シフト | 出勤打刻 | 退勤打刻 | 採用出勤 | 採用退勤 | 休憩 | 実働 | 残業 | 状態 | 備考 |
|---|---|---|---|---|---|---|---|---|---|---|---|

「打刻」列が生データ、「採用」列が丸め後。両方載せることで、なぜその時間になったかが一目で分かる。

### 7.3 管理者のみ閲覧できる仕組み

- スプレッドシートを**管理者の Google アカウントのみに共有**する。
- スタッフは Google アカウントを使わない（カードをかざすだけ）ので、**そもそもデータへのアクセス経路が存在しない**。
- ダウンロードはスプレッドシートの標準機能（ファイル → ダウンロード → Excel / CSV / PDF）でそのまま行える。専用機能を作る必要はない。

### 7.4 記録の保存

労働時間の記録は保存義務がある（賃金台帳等は5年、当分の間3年）。スプレッドシート上に year ごとに残り続けるため、運用上は自動的に満たされる。年度ごとにファイルを分けるかは運用で決める。

## 8. 打刻漏れ・修正の運用（紙より確実に良くなる点）

- 退勤打刻がないまま日付が変わったら、**管理画面に「要修正」として自動で上がる**。翌月末にまとめて発覚する、ということがなくなる。
- 翌朝そのスタッフがカードをかざしたとき、画面に注意書きを出して気づいてもらう。
- 管理者は管理画面から時刻を手入力で修正できる。
- **修正は必ず履歴が残る**（誰が・いつ・何を・何に変えたか）。元の打刻値も消えない。労基署対応・トラブル時の説明責任の観点で必須。

### 移行の進め方（提案）

1. フェーズ1完成後、**管理者だけで1週間テスト**する。
2. スタッフ数名（新しいことに抵抗の少ない方）で1週間試す。
3. 全員に展開。**最初の1ヶ月は紙と並行**して走らせ、集計が一致することを確認する。
4. 2ヶ月目から完全移行。

いきなり全面切替はしない。高齢スタッフが多い現場では、並行期間があること自体が安心材料になる。

## 11. 運用上の設定（実装とは別に必ずやること）

- **iPad の「アクセスガイド」を有効にする**（設定 → アクセシビリティ → アクセスガイド）。打刻画面から出られないよう固定する。これをやらないと、誤ってホームに戻る・別のサイトを開くといった事故が必ず起きる。**最重要。**
- iPad は電源に挿しっぱなし、自動ロック OFF、画面の明るさ固定。
- 打刻画面をホーム画面に追加しておく（万一閉じても復帰できるように）。
- Wi-Fi の安定を確認する。切れても打刻は端末に貯まるが、常時つながっている方がよい。

## 12. 未確定事項（実装前に確認したいこと）

1. **人数**（社員／パート合計何名か）— QRカードの発行枚数とシフト表の設計に影響
2. **拠点は1か所か**（iPad 1台想定でよいか）
3. **締め日**は月末でよいか（15日締めなどではないか）
4. **休憩の控除ルール**は上記の既定値（6h超45分／8h超60分）でよいか。就業規則の定めがあればそちらに合わせる
5. **管理者の Google アカウント**（既存のものを使うか、勤怠専用に作るか）
6. **残業の猶予時間**は15分でよいか
7. **深夜・休日の割増**を集計に含めるか（含めるなら深夜22時〜5時の時間帯集計を追加する）

これらは 1〜3 を除きフェーズ2以降で効いてくるので、フェーズ1の着手は先行できる。

## 13. 使用する Claude モデルの指針（クレジット節約）

### 前提: このシステムは**動作に AI を一切使わない**

打刻・判定・集計はすべて通常のプログラム処理。AI を使うのは**作るときだけ**。
したがって**稼働後の AI 費用は 0 円**。ここが SaaS との大きな違い。

### 作業別の使い分け

| 作業 | 推奨モデル | 理由 |
|---|---|---|
| 設計・仕様確定・丸め計算・締め処理などのロジック | **Opus 5** | ここをケチると設計ミスで作り直しになり、結果的に高くつく |
| 画面の HTML/CSS、単純な CRUD、文言修正 | **Sonnet 5**（`/model sonnet`） | Opus の半分以下の単価。この用途では品質差がほぼ出ない |
| 整形・リネームなどの単純作業 | **Haiku 4.5** | 最安 |

参考単価（1Mトークンあたり／入力・出力）: Opus 5 = $5 / $25、Sonnet 5 = $2 / $10、Haiku 4.5 = $1 / $5

### 消費を減らす実践的なコツ

1. **まとめて依頼する。** 「フェーズ1を全部作って」の方が、細かく何往復もするより圧倒的に安い。往復のたびにリポジトリを読み直すのが最大の無駄。
2. **セッションを分けすぎない。** 1つの作業は1セッションで終わらせる。
3. **この設計書をリポジトリに置いておく。** 次のセッションで一から説明し直す必要がなくなる（今回これを実施済み）。
4. **実装は Sonnet で始め、詰まったら Opus に上げる。** `/model` でいつでも切り替えられる。
5. 動作確認・微修正だけの日は Sonnet か Haiku で十分。
